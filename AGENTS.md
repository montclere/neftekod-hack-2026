# AGENTS.md

Инструкции для ИИ-агентов, работающих в этом репозитории.

---

## Принципы

Мы строим **инженерно состоятельное решение**. Код читают: жюри смотрит репозиторий,
технический эксперт задаёт вопросы по архитектуре. Ответ «мы торопились» баллов не приносит.

Три правила, из которых следует всё остальное:

1. **Сначала замысел, потом код.** Прежде чем писать, сформулируй, какую задачу решаешь
   и как она ложится на существующие границы. Задача больше часа — сначала план на обсуждение.
2. **Границы важнее скорости написания.** Логика живёт в одном месте, а не размазана
   по роутам и компонентам. Слой, который отвечает за всё, — ошибка проектирования.
3. **Сложность нужно заслужить.** Абстракция вводится, когда есть две реальные реализации,
   а не когда «может пригодиться». Это не разрешение хардкодить — это запрет на
   архитектуру ради архитектуры.

## Команды

```bash
make setup     # зависимости + .env-файлы, один раз после клона
make dev-api   # бэкенд на :8000
make dev-web   # фронтенд на :3000
make types     # TS-типы из OpenAPI  ← после любой правки схем Pydantic
make lint      # ruff + biome
make check     # бэкенд отвечает?
```

Запуск локальный, в двух вкладках терминала. Docker пока не собран
(`docker-compose.yml` нет) — когда появится, добавятся `make up` / `make down`,
и тогда же это место надо будет обновить.

**Правило:** любая команда, которую ты предлагаешь пользователю, должна существовать
в `Makefile`. Не выдумывай цели, которых там нет, — проверь файл.

## Архитектура

Что есть сейчас:

```
backend/app/
  main.py         FastAPI: health, CORS, пример роута
  api/            HTTP-слой: валидация входа, вызов сервиса, формирование ответа
  core/           предметная логика — здесь живёт суть системы
  ml/             инференс, эмбеддинги, промпты
  repo/           доступ к данным
frontend/src/
  app/            маршруты App Router
  components/     наши компоненты
  components/ui/  shadcn — не редактировать, см. ниже
  api/schema.d.ts сгенерированные типы, править нельзя
docs/
  CONTEXT.md      словарь предметной области
  adr/            записи о принятых решениях
```

Появится по ходу работы: `app/schemas.py` (контракт API), `app/seed.py` (демо-данные),
`app/eval.py` (замер метрик). Пакеты `api/`, `core/`, `ml/`, `repo/` сейчас пустые —
это границы, а не заготовки: наполняются по мере надобности.

**Направление зависимостей — строго внутрь.** `api` знает про `core`, `core` знает
про `repo`. Обратных связей нет: в `core` не импортируются объекты FastAPI, в `repo`
не попадает предметная логика.

**Роут — тонкий.** Если в функции роута появились ветвления по бизнес-правилам,
логика уехала не туда, вынеси в `core`.

## Язык предметной области

`docs/CONTEXT.md` — словарь проекта. Термины кейса, их точные значения, соответствие
именам в коде.

Заводишь новое понятие — сначала внеси его в словарь, потом называй им сущности.
Одна вещь называется одним словом во всём проекте: в коде, в интерфейсе, в README
и на слайдах. Расхождение между тем, как говорит заказчик, и тем, как называется
класс, — источник половины непонимания на защите.

Значимые развилки записывай в `docs/adr/` одним абзацем: что решили, какие были
альтернативы, почему выбрали это. На вопрос «почему не X» ответ должен быть готов заранее.

## Бэкенд

- Python 3.11 (`backend/.python-version`), зависимости через `uv`. `pip install` не использовать
- Pydantic v2. Все входы и выходы роутов типизированы — иначе ломается генерация типов фронта
- **Базы данных в проекте пока нет.** ORM, модели и миграции не подключены.
  Если кейс требует хранилища — это разговор и ADR, а не самостоятельное решение.
  Заранее выбранный вариант: PostgreSQL + pgvector, SQLAlchemy 2.0 (`select()`, не `query()`),
  без Alembic, схема через `create_all`
- **Аутентификации в проекте нет.** Пользователь захардкожен. Не добавляй логин,
  сессии, JWT и защиту роутов, даже если кажется, что без этого некрасиво
- Долгие операции — `StreamingResponse` + SSE. Интерфейс не должен ждать со спиннером
- Фоновые задачи — `BackgroundTasks`
- Ошибки: явные типы исключений в `core`, перевод в HTTP-коды на уровне `api`.
  Пустой `except:` и проглоченная ошибка недопустимы
- Логи структурные (`structlog`), с идентификатором запроса

## Фронтенд

- Next.js 16 App Router, TypeScript, Tailwind v4, shadcn/ui на Base UI
- **`components/ui/` не редактировать.** Это компоненты shadcn, на них завязаны все
  экраны. Нужна другая вёрстка — оборачивай в свой компонент. Если правка внутри
  кажется единственным выходом, сначала спроси
- Новый компонент ставится через `pnpm dlx shadcn@latest add <name>`
- Цвета, радиусы, отступы — только токены из `globals.css`. `bg-[#4F46E5]`
  и `text-slate-400` запрещены: они ломают тему и накапливаются незаметно
- Запросы — TanStack Query. Голый `fetch` в компонентах не использовать
- Формы — react-hook-form + zod
- Состояния загрузки, пустоты и ошибки обрабатываются всегда. Экран, который
  показывает пустоту вместо объяснения, считается незаконченным
- Линтер и форматтер — **biome**, не eslint. `make lint` должен быть зелёным перед коммитом.
  `src/components/ui/`, `src/api/` и `public/` из проверки исключены намеренно:
  это вендорный и сгенерированный код

## Граница фронта и бэка

**Типы API руками не пишутся.** Они генерируются из OpenAPI.

Поменял схему Pydantic — скажи явно и напомни про `make types`.
Фронту не хватает поля — добавь его в схему бэка, не в тип фронта.
`frontend/src/api/schema.d.ts` сгенерирован, правки затрутся.

Файл лежит в репозитории (решение осознанное: без него у напарника после клона
не типизируется фронт). После `make types` он попадает в обычный коммит.
Конфликт при слиянии в нём разрешается не руками, а повторным `make types`.

## Данные и ML

- Модели с нуля не обучаем: готовые эмбеддинги, LLM через API, CatBoost на табличных задачах
- LangChain и LlamaIndex не добавлять. Обёртка над LLM своя, в `app/ml/` —
  чужая абстракция усложняет отладку ровно тогда, когда она нужнее всего
- Промпты — в отдельном модуле, версионируются вместе с кодом, не размазаны по вызовам
- Векторный поиск, если понадобится, — через pgvector, отдельная векторная БД не нужна
- Любая метрика из README воспроизводится одной командой. Скрипт замера
  (`app/eval.py` + цель `make eval`) ещё не написан — пока его нет, чисел в README быть не должно

## Соразмерность

Не берём, потому что для одного сервиса и одной базы это неверные решения,
а не потому что нет времени:

- микросервисы, очереди сообщений, Kubernetes
- GraphQL поверх десятка эндпоинтов
- аутентификация в любом виде — ни своя, ни через библиотеку
- миграции Alembic
- слои-обёртки и интерфейсы с единственной реализацией

Если кажется, что что-то из этого нужно, — это разговор, а не самостоятельное решение.

## Стабилизация перед сдачей

Когда я скажу «стабилизация», проект переходит в другой режим:

- новые возможности не добавляются
- правится только то, что видно в демо-сценарии
- рефакторинг останавливается, даже полезный
- каждое изменение минимальное из возможных, каждое сопровождается прогоном
  демо-сценария целиком
- README, схема архитектуры и ADR приводятся в соответствие с тем, что в коде
